# TRL0037 — Claim task ids from a local git ledger

## Problem

SPEC §3 assigns ids from `nextId`, the highest id on the current branch plus
one (`nextId` in `src/backlog.mjs`). Two branches, or two worktrees, read the
same highest id and claim the same next one. Taproot hit this on 2026-11-12:
three sessions writing stories in parallel worktrees claimed overlapping ids
and had to renumber after review.

## Scope

- **Config (SPEC §7).** A new optional key, `idAllocation`, is `"scan"`
  (today's behavior, the default) or `"ledger"`. A second optional key,
  `idLedgerRef`, names the ledger ref and defaults to `refs/trellis/ids`.
  Validation rejects any other `idAllocation` value and any ref outside
  `refs/trellis/` (scope cut 2026-11-19: no `refs/heads/` ledgers, so a
  ledger can never land on a branch). In ledger mode `idWidth` must be at
  most 9, so id arithmetic stays exact in JavaScript numbers. The
  namespace lives outside `refs/heads/` for two reasons: branch cleanup (`git branch -D`, worktree
  pruning) never sees it, and `git push --all` never publishes it. All
  worktrees of a clone still share it.
- **Spec version.** This story owns the bump from `specVersion` 2.4 to 2.5
  (additive). It changes:
  - SPEC.md's header and §9 entry;
  - `SPEC_VERSION` in `src/backlog.mjs`;
  - this repo's `trellis/backlog.config.json`;
  - the `specVersion` line in `AGENTS.md`;
  - the version literal asserted in `test/init.test.mjs`.

  TRL0038, TRL0039 and TRL0040 add their keys under 2.5 while it is
  unreleased. They land in the order TRL0037, TRL0038, TRL0039, then
  TRL0040, as sequential commits on one branch with one PR (owner decision
  2026-11-19, recorded in `trellis/completed/tasks/TRL0036.md` and the
  Taproot session's notes). All four edit `src/init.mjs`, SPEC §7 and
  `docs/import.md`.
- **Ledger format (new SPEC §3.1).** The ledger is an orphan branch whose tip
  tree holds one file, `claims.tsv`. Its first line is exactly
  `id<TAB>date<TAB>kind<TAB>branch<TAB>title`. Each later line is `id<TAB>date<TAB>kind<TAB>branch<TAB>title`:
  - `date` is an ISO date;
  - `kind` is `seed`, `claim` or `through`;
  - `branch` is the worktree's branch, or `-` when detached or for
    `through`;
  - `title` is a single line with no tabs or control characters; titles
    read from item files for seed lines are sanitized the same way.

  Every reader validates every row (five fields, an id matching
  `idPrefix`/`idWidth`, a real date, a known kind) before using the tip,
  and treats any bad row as "not a ledger". It never skips a row, since a
  skipped high-water row could hand out a reserved id again. Only `claim`
  lines whose id has no item file are "open" claims (TRL0041
  lists only those). Lines are only ever appended. Each claim is one commit whose
  parent is the previous tip.
- **One literal id matcher.** This story adds one shared matcher that
  treats `idPrefix` literally (escaped, never interpolated into a regex).
  `readBacklog`, the MCP id checks (`get_task`, `move_task`) and the
  ledger all use it, so an id the ledger issues is always addressable.
  TRL0005 reuses it.
- **Git helper hygiene.** The shared ledger git helper runs every command
  with `GIT_NO_REPLACE_OBJECTS=1`, so a replacement object cannot show a
  lower high-water mark than the real tree.
- **Atomic claim (`src/ledger.mjs`, new).** A claim works only with git
  plumbing:
  1. Read the tip with the exact lookup below (`git show-ref --verify
     --hash <ref>`), which every ledger read uses.
  2. Compute the next id as max(highest id in the ledger or any worktree's
     task tree + 1, `nextIdFloor`). This matches SPEC §7's `nextId` rule. The worktree scan matches
     filenames against the served config's `tasksDir`, `idPrefix` and
     `idWidth`. It does not validate items, and it skips missing or
     prunable worktrees, so a lane with an invalid tree cannot block a
     claim.
  3. Write the new `claims.tsv` blob (`git hash-object -w --stdin`), then
     the tree (`git mktree`), then the commit (`git commit-tree -p <old>`).
  4. Move the ref with `git update-ref --no-deref --create-reflog <ref>
     <new> <old>`. The reflog flag matters because git keeps no reflog for
     refs outside `refs/heads/` by default.

  Before step 3, an id above `10^idWidth − 1` (for example `TRL10000` at
  width 4) fails the claim with exit 2 and no ledger
  write.

  `update-ref` with an old value is a compare-and-swap. If another claim
  moved the tip first, it fails, and the claim re-reads the tip and retries,
  up to 10 times before it errors. All worktrees of a clone share refs, so
  every session on one machine sees each claim immediately. Nothing is
  pushed.
- **Seeding.** `trellis claim --seed` creates the ledger when it is absent.
  Its first commit records one `seed`-kind line per id found in the task tree of
  every worktree of the clone (`git worktree list --porcelain`), with
  `branch` set to the worktree's branch. That way an id held only on a lane
  branch is never handed out again. `--seed --through <ID>` additionally
  records a high-water mark for ids held on branches that are not checked
  out anywhere. When the ref already exists, `--seed` exits 0 without
  writing.
- **High-water lines.** SPEC §3.1 tells operators to pause other writers
  while `--through` reserves ids held on branches with no worktree, and to
  check `--list` for claims in that range before resuming, because a claim
  that wins the compare-and-swap first may already have issued one of
  those ids. `trellis claim --through <ID>` appends one line,
  `<ID><TAB><date><TAB>through<TAB>-<TAB>-`, to an existing ledger. `--seed
  --through <ID>` writes the same line in the seed commit. A `through` line
  counts as recording every id up to and including it.
- **Claims also scan worktrees.** The next id is computed over the ledger,
  every worktree's task tree and `nextIdFloor`. A story written before the
  seed, in a worktree, is never shadowed.
- **CLI.** `trellis claim --title "<one line>"` claims the next id, prints
  it, and exits 0. It exits 2 when `idAllocation` is not `"ledger"` or the
  ledger does not exist (the message names `trellis claim --seed`), and 1
  when the retries run out. `trellis claim --list` prints the tip's object id and the ledger lines.
  Wire it through `scripts/trellis.mjs` with a `--help` entry.
  Mode matrix:
  - `--seed` works in either mode, before or after the config switches to
    ledger;
  - `--through` and `--list` exit 2, naming `--seed`, when the ref is
    absent;
  - only `--title` requires `idAllocation` `"ledger"`.
- **Uniqueness scope.** The guarantee holds among writers that use ledger
  mode with the same ref and compatible `idPrefix`, `idWidth` and
  `tasksDir` settings. SPEC §3.1 documents the cutover: switch every open
  worktree's config to ledger mode in the same change, by merging or
  rebasing it, before claiming. A lane still in scan mode can pick an open
  claim's id until it rebases.
- **MCP (`src/mcp.mjs`, registered in `scripts/trellis-mcp.mjs`).**
  - A new `claim_id` tool wraps the claim.
  - In ledger mode, `create_task` claims through the ledger instead of
    calling `nextId`. When the ledger ref is absent, it fails with the same
    `trellis claim --seed` message as the CLI. It never falls back to the
    scan, so a fresh clone cannot hand out a used id. If a write fails
    after the claim, it rolls back the item and generated files as today,
    and the claimed id stays claimed. Rollback never touches the ledger, so
    it cannot release an id or drop a later claim. Ids are never reused
    (SPEC §3).
  - `next_id` reports the ledger's next id without claiming, and its result
    says that the value is a preview. With the ref absent, it returns
    `nextId: null` and the `--seed` guidance, matching `list_tasks` and
    `regenerate`.
  - The tool schemas and descriptions for `claim_id`, `next_id` and
    `create_task` in `scripts/trellis-mcp.mjs` describe the ledger
    behavior.
- **No hand-picked ids in ledger mode.** In ledger mode, `trellis generate`
  prints "claim ids with `trellis claim`" instead of "Next id:". The
  `nextId` that `list_tasks` and `regenerate` return is the ledger preview
  when the ref exists, and otherwise `null` with the same note.
- **Validation is unchanged.** `check` does not read the ledger. SPEC
  §8.3 forbids `check` from depending on volatile local state, and ids
  claimed in another clone or session would arrive above this clone's
  ledger and fail for no real reason. The ledger's job is allocation:
  every claim takes every worktree's ids into account, and duplicate ids
  are still caught by the existing duplicate-id rule.
- **`backlog.json`.** In this story every on-disk `backlog.json` keeps the
  scan `nextId`, including after an import, because a committed file must
  be the same in CI, which has no ledger (SPEC §8 determinism). TRL0038
  adds the local-mode output path and wires the ledger preview into it.
  SPEC §3 is amended: in ledger mode, `trellis claim` and the MCP claim
  path hand out ids, not the published `nextId`.

- **Safety and robustness.**
  - `idLedgerRef` is checked in the core config validator without git,
    using the `git check-ref-format` rules as a pattern: no `..`, `//`,
    `@{`, space, DEL or other control characters, and none of `~^:?*[\`;
    not a lone `@`; no leading or trailing `/`; no trailing `.`; no
    component starting with `.` or ending in `.lock`. `check` therefore validates it on a host without
    git.
  - The ref is read exactly with `git show-ref --verify --hash <ref>`,
    never with revision lookup, which could resolve a same-named ref
    elsewhere. Ledger operations refuse a symbolic ref, including a
    dangling one (`git symbolic-ref -q <ref>` succeeds), and every write
    uses `update-ref --no-deref`.
  - `idPrefix` must contain no tab, newline or control character for any
    operation that writes ledger rows, including `--seed` and `--through`
    in scan mode, so it cannot break a ledger line.
  - `claim` and `--seed` refuse an existing ref whose tip tree is not
    exactly one valid `claims.tsv`.
  - `--seed` creates the ref with `git update-ref --no-deref
    --create-reflog <ref> <new> 0000…` (all-zero old value), so two
    concurrent seeds cannot overwrite each other. On failure it re-reads
    the ref: if a valid ledger now exists, it exits 0 saying so; otherwise
    (a lock or permission error) it exits 1 with git's message.
    `--seed --through` on an existing ledger prints that nothing was
    written and names `claim --through`.
  - `--through` uses the same compare-and-swap and retry as a claim, so it
    never overwrites a concurrent claim.
  - Commits use the repo's git identity. When none is configured,
    `commit-tree` runs with `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME` `trellis`
    and `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL` `trellis@localhost`, so a
    fresh clone or cloud session can still claim.
  - `--title` and the `claim_id` title get the same single-line check as
    `oneLine` in `src/mcp.mjs`, and tabs and control characters are
    rejected, so a title cannot forge a ledger line. `--through <ID>` must
    match `idPrefix` and `idWidth`, or the command exits 2.
  - `claim` takes `--target`/`--repo` like the other commands.
  - `claim`, `--seed` and `--list` exit 2 with a clear message when git is
    missing, the directory is not a git repo, the ref's tip is not a
    ledger, or the repo uses the reftable ref format (`git rev-parse
    --show-ref-format`), which is out of scope. `check` never calls git.
  - Worktrees are enumerated with `git worktree list --porcelain -z`, so a
    path containing a newline is read correctly.
  - When the next id would exceed `idWidth`, or the ledger is unusable,
    every preview (`next_id`, `list_tasks`, `regenerate`, the `generate`
    note) is `null` with the reason: exhausted, invalid ref, or git
    unavailable.
  - Concurrent writers that regenerate files in the same worktree are not
    serialized. SPEC §3.1 says to run one file-writing Trellis command per
    worktree at a time; the ledger itself stays safe across worktrees.
- **Import is out of scope in ledger mode (scope cut 2026-11-19).**
  Import into a ledger-mode backlog is unsupported. The shared importer
  refuses before planning, for both preview (`--dry-run`) and `--apply`,
  with exit 2, and so does MCP `import`. `init --import` refuses before
  any scaffolding, even with `--force`, by reading the existing config
  first. The message and `docs/import.md` say to import before switching
  to ledger mode and seeding. Importing in scan mode into an already
  seeded backlog could assign an id that is an open claim.
- **Keeping git out of the core.** `src/backlog.mjs` stays free of git, as
  the header of `src/history.mjs` requires, so `check` never depends on
  git. `generateArtifacts` and `buildBacklogJson` take an optional
  `nextIdOverride`: `undefined` means compute the scan value, and an
  explicit `null` is emitted as `null`. In this story, no writer passes an
  override, so every file on disk keeps the scan value. The previews
  returned by MCP `regenerate`, `list_tasks` and `next_id`, and the
  `generate` note, are computed separately through `src/ledger.mjs`.
  TRL0038 is the first to pass an override, for local-mode files.
  `check` never passes one.

## Acceptance

- `node --test` covers each of these in a temporary git repository with a
  linked worktree:
  - Two worktrees claiming concurrently get distinct, consecutive ids. A
    test forces the compare-and-swap to lose once and shows the retry.
  - `--seed` is idempotent.
  - `--seed` records an id that exists only in the linked worktree, and
    honors `--through`.
  - `create_task` in ledger mode claims, and the id stays claimed after a
    forced rollback.
  - `--through` on an existing ledger appends one line, and the next claim
    is above it.
  - A floor-only ledger (`nextIdFloor` 1000, no higher ids) hands out
    1000.
  - In ledger mode, `generate` prints the claim note, not "Next id:".
  - `--list` shows `seed`, `claim` and `through` in the kind column.
  - With the ref absent, `create_task` in ledger mode fails with the seed
    message.
  - A committed-mode `backlog.json` is identical with and without the
    ledger ref.
  - A tip whose tree is not a ledger is refused, and the ref is unchanged.
  - Two concurrent `--seed` runs leave one seed commit.
  - A claim succeeds with `user.name` and `user.email` unset.
  - A title containing a newline or tab is rejected (exit 2).
  - `--seed` in scan mode creates the ledger. `--through` and `--list` with
    the ref absent exit 2.
  - A failed write after a claim keeps the ledger line, and the item and
    generated files are restored.
  - `trellis import` (`--dry-run` and `--apply`), MCP `import` and `init
    --import --force` all refuse in ledger mode before any write.
  - A ledger row with a bad field makes the tip "not a ledger".
  - A seed that loses to a lock error exits 1; one that loses to another
    valid seed exits 0.
  - `idWidth` 10 in ledger mode is a config error, and an `idLedgerRef`
    under `refs/heads/` is a config error.
  - A worktree path containing a newline is scanned.
  - At the width limit, `next_id` returns `null` with "exhausted".
  - `check` passes with a valid `idLedgerRef`, no ledger and git
    unavailable.
  - After `generate` and MCP `regenerate` with an open claim, the on-disk
    `backlog.json` holds the scan `nextId`.
  - `--through` racing a claim keeps both lines.
  - A claim at the width limit fails with exit 2 and no write.
  - A symbolic `idLedgerRef` is refused. A malformed one, such as
    `refs/trellis/my ids`, is a config error from `check` with git
    unavailable.
  - Config errors for a bad `idAllocation` or an `idLedgerRef` that fails
    `check-ref-format`.
  - `claim` exits 2 in scan mode, and exits 1 when retries run out (forced).
  - `next_id` in ledger mode returns the preview without changing the ref.
  - Scan mode is byte-for-byte unchanged: existing tests pass untouched
    except the version literal.
- `npm run backlog:check` and `node --test` exit 0.
- SPEC.md documents `idAllocation`, `idLedgerRef` and §3.1, says `check`
  does not read the ledger, and the 2.5 entry says it is additive.

## Notes

- **Owner decision 2026-11-19: local only.** No push, no remote, no network.
  Sharing ids across machines is a later, separate decision: it would mean
  pushing one ref, with a ruleset that blocks force-push and deletion.
- Rejected: a lock file under `.git`. Linked worktrees have their own
  `.git` file, so finding the common directory needs `git rev-parse
  --git-common-dir`, and a stale lock needs recovery. The ref
  compare-and-swap is atomic in git itself and leaves an auditable history.
- Rejected: GitHub Issues as the number dispenser. It needs the network and
  credentials in every session.
- Rejected (2026-11-19 review): having `check` fail ids above the ledger's
  mark. It made `check` depend on local state, against SPEC §8.3, and it
  failed ids legitimately claimed in another clone.
- The ledger never holds story text. The task file stays the source of
  truth, and the ledger only proves an id was handed out once.

## Risks

- Hosts that block git plumbing writes. Mitigation: every git call goes
  through one helper that reports the failing command, and scan mode stays
  the default.
- A claim that is never written leaves a gap in the numbering. Gaps are
  allowed (SPEC §3 forbids reuse, not gaps), and `--list` shows them.
- `git gc` never prunes a ref's history, so the ledger is safe from gc.
- Someone deleting the ref by hand (`git update-ref -d`) loses the ledger.
  Mitigation:
  `claim` refuses to run without the ref and names `--seed`. `update-ref
  -d` can remove the reflog too, so recovery restores a tip whose object id
  was saved (`--list` prints the tip id), or re-seeds with `--through` set
  to the last known high-water mark. A plain re-seed sees only ids with
  files and could hand out a lost claim again. The missing-ref message
  says this.

## Refinements

Decisions taken at plan time (2026-11-19). Each carried review finding was
checked against the code. The accepted ones are part of Scope.

Stale assumptions in the story, checked against the code:

- `readBacklog` (`src/backlog.mjs:439,480`) and `idRegex` (`src/mcp.mjs:177`)
  both interpolate `idPrefix` into a regex unescaped. Today a prefix with a
  regex character or `/` is silently accepted. The shared matcher fixes this
  for all three call sites. Scan mode keeps its current accepted prefixes
  (no new config error there), so only ledger mode adds prefix limits.
- `writeArtifacts` (`src/mcp.mjs:193`) restores prior bytes on failure but
  writes in place. The story's "restore" wording is right, and the atomic
  replace below is an addition.
- `trellis generate` prints "Next id:" from `scripts/backlog-readme.mjs`.
  That script loads the config, so it can read `idAllocation` there.
- `init --import` calls `applyScaffold` before `applyImport`
  (`scripts/trellis-init.mjs`), so the shared importer's refusal alone is too
  late. The init wrapper reads the existing config first.
- Local git is 2.55. The ledger commands need `git worktree list -z` (2.36),
  `rev-parse --show-ref-format` (2.41) and `GIT_NO_LAZY_FETCH` (2.44), so the
  minimum is git 2.44. Confirm the 2.44 figure against the git release notes
  when writing the probe.

Accepted carried findings, folded into Scope:

- **Prefix limits.** In ledger mode, and for any command that writes ledger
  rows, `idPrefix` must match `^[A-Za-z0-9_-]+$` (no path separator, `.`,
  control character or space). `check` reports it as a config error in ledger
  mode. `--seed` and `--through` in scan mode refuse with exit 2. This runs
  before any id is allocated.
- **Checkout containment.** The worktree scan lists a task directory only
  when its real path stays inside that worktree's real path. A symlinked
  `tasksDir`, `active` or `completed/tasks` that leaves the checkout is
  skipped, never read.
- **Sparse checkouts.** The scan unions on-disk filenames with
  `git -C <worktree> ls-files -z -- <tasksDir>`, filtered by the same
  matcher, so a skip-worktree item still counts. If `ls-files` fails for a
  worktree, the claim refuses (exit 2) rather than guess.
- **Cutover.** SPEC §3.1 and the 2.5 entry say: upgrade and restart every CLI
  and MCP writer first, since an older Trellis ignores `idAllocation` and
  keeps scanning. Pause scan-mode writers until every worktree has merged the
  ledger config and the seed has run.
- **Atomic artifact writes.** `writeArtifacts` writes each artifact to a
  temp file in the same directory and renames it over the target, so a failed
  write never leaves a half file. The existing restore stays. Test: make one
  artifact path unwritable (a directory in its place) and assert every
  artifact keeps its prior bytes. The CLI `generate` path keeps its plain
  writes (no change in scan mode).
- **Commit check.** The ref's object must be a commit (`git cat-file -t`
  prints `commit`) before its tree is read. A tag or tree is "not a ledger".
- **Git capability.** One probe in `src/ledger.mjs` checks `git --version`
  is at least 2.44 and that `git rev-parse --show-ref-format` prints exactly
  `files`. Any other result (older git, an unknown flag, `reftable`, an
  error) exits 2 with the reason. `check` never runs the probe.
- **Previews.** Tests run both `generate` and MCP `regenerate` twice: with an
  open claim, and with a null ledger preview (ref absent). Each keeps the scan
  `nextId` on disk.
- **No lazy fetch.** The shared helper also sets `GIT_NO_LAZY_FETCH=1` and
  `GIT_TERMINAL_PROMPT=0`. A missing local object (`cat-file`, `ls-tree`,
  `show` fails) makes the ledger unusable, with the same exit 2 as "not a
  ledger". It never fetches.
- **Recovery.** The missing-ref message and SPEC §3.1 say to restore from a
  tip id saved from `--list`, after checking it is a commit with a valid
  `claims.tsv`, or to re-seed with `--through` set to a confirmed upper bound
  on every id ever allocated, not just the last one seen.

Rejected: none. Every carried finding holds against the code.
