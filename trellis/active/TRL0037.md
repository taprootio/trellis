# TRL0037 — Claim task ids from a local git ledger

## Problem

SPEC §3 assigns ids from `nextId`, the highest id on the current branch plus
one (`nextId` in `src/backlog.mjs`). Two branches, or two worktrees, read the
same highest id and claim the same next one. Taproot hit this on 2026-11-12:
three sessions writing stories in parallel worktrees claimed overlapping ids
and had to renumber after review.

## Scope

- **Config (SPEC §7).** A new optional key, `idAllocation`, is `"scan"`
  (today's behavior, the default) or `"ledger"`. A second optional key,
  `idLedgerRef`, names the ledger ref and defaults to
  `refs/heads/trellis-ids`. Validation rejects any other `idAllocation` value
  and any ref that is not under `refs/heads/`. Bump `specVersion` 2.4 → 2.5
  (additive) in SPEC.md and in this repo's `trellis/backlog.config.json`.
- **Ledger format (new SPEC §3.1).** The ledger is an orphan branch whose tip
  tree holds one file, `claims.tsv`. Its first line is a header. Each later
  line is `id<TAB>claimed_on<TAB>branch<TAB>title`, where `claimed_on` is an
  ISO date and `branch` is the claiming worktree's branch, or `-` when
  detached. Lines are only ever appended. Each claim is one commit whose
  parent is the previous tip.
- **Atomic claim (`src/ledger.mjs`, new).** A claim works only with git
  plumbing:
  1. Read the tip with `git rev-parse --verify <ref>`.
  2. Compute the next id as max(highest id in the ledger, highest id in any
     worktree's task tree, `nextIdFloor`) + 1.
  3. Write the new `claims.tsv` blob (`git hash-object -w --stdin`), then
     the tree (`git mktree`), then the commit (`git commit-tree -p <old>`).
  4. Move the ref with `git update-ref <ref> <new> <old>`.

  `update-ref` with an old value is a compare-and-swap. If another claim
  moved the tip first, it fails, and the claim re-reads the tip and retries,
  up to 10 times before it errors. All worktrees of a clone share refs, so
  every session on one machine sees each claim immediately. Nothing is
  pushed.
- **Seeding.** `trellis claim --seed` creates the ledger when it is absent.
  Its first commit records one `seed` line per id found in the task tree of
  every worktree of the clone (`git worktree list --porcelain`), with
  `branch` set to the worktree's branch. That way an id held only on a lane
  branch is never handed out again. `--seed --through <ID>` additionally
  records a high-water mark for ids held on branches that are not checked
  out anywhere. When the ref already exists, `--seed` exits 0 without
  writing.
- **Claims also scan worktrees.** The next id is computed over the ledger,
  every worktree's task tree and `nextIdFloor`. A story written before the
  seed, in a worktree, is never shadowed.
- **CLI.** `trellis claim --title "<one line>"` claims the next id, prints
  it, and exits 0. It exits 2 when `idAllocation` is not `"ledger"` or the
  ledger does not exist (the message names `trellis claim --seed`), and 1
  when the retries run out. `trellis claim --list` prints the ledger lines.
  Wire it through `scripts/trellis.mjs` with a `--help` entry.
- **MCP (`src/mcp.mjs`).**
  - A new `claim_id` tool wraps the claim.
  - In ledger mode, `create_task` claims through the ledger instead of
    calling `nextId`. If its write fails it rolls back the file as today,
    and the claimed id stays claimed. Ids are never reused (SPEC §3).
  - `next_id` reports the ledger's next id without claiming, and its result
    says that the value is a preview.
- **Validation (SPEC §8.3).** When `idAllocation` is `"ledger"` and the
  ledger ref exists in the repository, `check` fails for any task id that is
  neither seeded nor claimed. When the ref is absent, as in a CI checkout,
  which never fetches it, `check` warns once and skips this rule. Validation
  must never depend on a ref that CI does not have.
- **`backlog.json`.** In ledger mode, `nextId` comes from the ledger when the
  ref exists and from the scan otherwise. Every other field is unchanged.

## Acceptance

- `node --test` covers each of these in a temporary git repository with a
  linked worktree:
  - Two worktrees claiming concurrently get distinct, consecutive ids. A
    test forces the compare-and-swap to lose once and shows the retry.
  - `--seed` is idempotent.
  - `--seed` records an id that exists only in the linked worktree, and
    honors `--through`.
  - `check` passes with seeded and claimed ids, and fails on an unclaimed
    id while the ref exists.
  - `check` warns and passes when the ref is absent.
  - `create_task` in ledger mode claims, and the id stays claimed after a
    forced rollback.
  - Scan mode is byte-for-byte unchanged: the existing tests pass untouched.
- `npm run backlog:check` and `node --test` exit 0.
- SPEC.md documents `idAllocation`, `idLedgerRef`, §3.1 and the validation
  rule, and the 2.5 entry says it is additive.

## Notes

- **Owner decision 2026-11-19: local only.** No push, no remote, no network.
  Sharing ids across machines is a later, separate decision: it would mean
  pushing one ref, with a ruleset that blocks force-push and deletion.
- Rejected: a lock file under `.git`. Linked worktrees have their own
  `.git` file, so finding the common directory needs `git rev-parse
  --git-common-dir`, and a stale lock needs recovery. The ref
  compare-and-swap is atomic in git itself and leaves an auditable history.
- Rejected: GitHub Issues as the number dispenser. It needs the network and
  credentials in every session.
- The ledger never holds story text. The task file stays the source of
  truth, and the ledger only proves an id was handed out once.

## Risks

- Hosts that block git plumbing writes. Mitigation: every git call goes
  through one helper that reports the failing command, and scan mode stays
  the default.
- A claim that is never written leaves a gap in the numbering. Gaps are
  allowed (SPEC §3 forbids reuse, not gaps), and `--list` shows them.
- `git gc` never prunes a ref's history, so the ledger is safe from gc.
