# TRL0035 — Dogfood round 2: onboard Taproot in place with the published release

## Scope

- Taproot does the work in its own backlog. Its adoption task (the next
  `TR` id, in `docs/tasks/active/`) replaces `scripts/backlog-readme.mjs`
  with the published package. This task tracks the Trellis side.
- Taproot's backlog is already Trellis-shaped (`docs/tasks/{active,
  completed/tasks,removed}`), so it is onboarded in place with `trellis
  init` and a config, not with `trellis import`. The config is:
  - `idPrefix` `TR`, `idWidth` 5, `tasksDir` `docs/tasks`;
  - Taproot's milestone order;
  - `idAllocation` `"ledger"` (TRL0037);
  - `generatedArtifacts` `"local"` (TRL0038);
  - `legacyThrough` set to the highest id at adoption (TRL0039).

  Init runs with `--skip ci,pr-template`, and good-agent detection skips
  the playbooks (TRL0040).
- Use only the published `npx @taprootio/trellis`, at the release that
  carries TRL0037–TRL0040, in a fresh context. Do not read the Trellis
  source.
- Record friction verbatim in this task's Outcome, and file anything that
  needs a Trellis change as a new story.

## Acceptance

- In the Taproot adoption branch, `npx @taprootio/trellis check` exits 0
  and `trellis claim --seed` then `trellis claim` hand out the next id.
- The Outcome lists every friction point found, or states that there were
  none.

## Notes

- Revised 2026-11-19. The first plan was to re-import Taproot with the
  built-in profile. In-place onboarding is the real path for a repo that is
  already Trellis-shaped. The checks against TRL0031–TRL0034 still apply
  where import is touched.
- The first dogfood (TRL0010) proved the onboarding mechanism. It also
  surfaced the id, summary and scaffolding friction that TRL0031–TRL0034
  fixed.

## Risks

- The release must be on npm before this runs. The dogfood installs the
  published package and must not use a sibling checkout.
