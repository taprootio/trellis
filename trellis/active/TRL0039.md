# TRL0039 — Accept closed items that predate a repo's adoption

## Problem

`readBacklog` in `src/backlog.mjs` (`checkHistorical`) requires `summary`,
`milestone`, `priority` and `effort` on every completed and removed item.
`trellis init` refuses to scaffold a repo whose backlog has errors.

Taproot's backlog is already Trellis-shaped, but its archive is older than
those rules. On 2026-11-19, `trellis check` on a copy of it reported 1,995
errors:
- 873 completed items missing `milestone`;
- 768 missing `summary`;
- 103 missing `priority` and `effort`;
- 132 removed items missing `milestone`, and 13 missing `summary`.

The only way through today is to make up values for about a thousand
finished tasks.

## Scope

- **Config (SPEC §7).** A new optional object, `legacy`, has exactly two
  required fields. Any other key, a `null` value, or a non-object is a
  config error:
  - `through`, a full id in the repo's format (for example `TR01388`),
    checked by prefix, then a fixed `/^\d+$/` on the remainder with
    length equal to `idWidth`, never by a regex built from `idPrefix`;
  - `closedBefore`, a real calendar date (`YYYY-MM-DD`, checked as a date,
    so `2026-02-31` is a config error): the adoption date, exclusive.

  `through` must match `idPrefix` and `idWidth`. When `legacy` is present,
  `idPrefix` must also be a plain prefix, checked with the existing
  `PLAIN_PREFIX_RE` in `src/backlog.mjs` (the rule ledger mode uses; one
  owner, not copied): any other prefix with `legacy` is a config error.
  The scan regex would otherwise read `T.P` or `T+P` as regex syntax and
  skip or mis-match archive files. Without `legacy`, prefixes behave as
  today. The key is added under
  `specVersion` 2.5 (no version change), after TRL0038.
- **Who qualifies (SPEC §5.1, §8.3).** A completed or removed item
  qualifies when both are true:
  - its id is at or below `legacy.through`;
  - its recorded `completed_on` or `removed_on` is a real calendar date
    strictly before `legacy.closedBefore`.

  An item that is still open at adoption and closes on adoption day or
  later fails the date test, so it must carry the full snapshot.
- **Close dates.** A repo without `legacy` keeps today's date check (the
  `YYYY-MM-DD` shape). A repo with `legacy` also rejects a well-shaped but
  impossible close date on any completed or removed item as an item error,
  since qualifying depends on it. One shared helper owns "real calendar
  date" for the config and the items.
- **What qualifying changes.** For a qualifying item, `summary`,
  `milestone`, `priority` and `effort` are optional. In a repo with
  `legacy`, a blank value (an empty or whitespace-only string, quoted or
  not) counts as missing on every completed and removed item, so a
  non-qualifying item with a blank value fails with today's "missing"
  message. Everything else is still enforced: `id`, `title`, `status`,
  `depends_on`, the close date and `removed_reason`. The blank rule
  applies to closed items only: active items are validated exactly as
  today, so a quoted whitespace-only active `summary` still passes. Two rules differ in a repo with `legacy`:
  the close-date rule above and the blank rule. A repo without `legacy`
  is byte-for-byte unchanged, in checks and in output.
- **Rendering (SPEC §6.2, §6.3, §8.1, §8.2, §8.5).** The four fields are
  nullable for a qualifying item. The read step turns a blank value into a
  missing one, so every renderer, committed and local, sees the same item:
  - in `backlog.json`, a missing or blank value is `null`, effort included;
  - the effort display fields (`effortLabel`, `effortEmoji`,
    `effortImage`) are omitted when effort is missing;
  - the generated tables show an empty cell.

  SPEC states this exception where it promises a resolved effort number.
- **Init (in-place onboarding).** `trellis init` validates the archive
  with the config it will keep, so a repo writes `legacy` into its config
  first and runs init without `--force`. Init's `--help` and
  `docs/import.md` say so. `init --force` is refused before any write
  (exit 2, through the `ImportRefused` handler beside the local-mode
  refusal) whenever the raw existing config has a `legacy` key, read the
  same way as `assertNotLocalMode` and with no validity test, whatever its
  `tasksDir`: the replacement config would drop `legacy` and its default
  `tasksDir` could point preflight at an empty tree. Without `legacy` in
  the existing config, `--force` keeps validating with the replacement,
  as today.
- **Import is unchanged.** Import planning (`src/import.mjs`, the
  closed-item check near line 585) requires milestone, priority and
  effort for every closed item from every profile, including the built-in
  `trellis` profile, and keeps doing so. The import guide says `legacy`
  covers in-place onboarding of a Trellis-shaped backlog only. Import
  into a repo that has `legacy` reads the archive under the same rules.
- **Docs.** SPEC.md §5.1, §6.2, §6.3, §7, §8.1, §8.2, §8.3 (validation
  item), §8.5 (the local `backlog.json` carries the same nulls) and the
  §9 2.5 paragraph.

## Acceptance

- `node --test` covers these, with a fixture under `test/fixtures/`
  (`legacy-adoption/`) holding closed items that omit the four fields:
  - A completed item whose id equals `legacy.through`, without the four
    fields, validates. With them blank, including a quoted `"   "`, it
    also validates and emits `null`.
  - The same item one id above `through` fails with today's messages.
  - An item at or below `through` closed on the adoption date itself fails
    with today's messages.
  - A removed item inside both bounds without `removed_reason` still fails.
  - An item inside both bounds without `depends_on` still fails.
  - A missing or malformed `through`, or an impossible `closedBefore`,
    is a config error. With `legacy` set, an impossible close date on an
    item is an item error, including a fully populated item above
    `legacy.through` dated `2026-02-31`. Without `legacy`, today's behavior is
    unchanged.
  - `init --force` with a `legacy` config and a custom `tasksDir` is
    refused before any write.
  - A blank value on a non-qualifying closed item in a repo with `legacy`
    fails with today's "missing" message; the same item in a repo without
    `legacy` is unchanged.
  - `legacy` with an extra key, a `null` value or a non-object is a config
    error, and so is `legacy` with a non-plain `idPrefix` such as `T.P`
    or `T+P`.
  - Positive init fixture: with `legacy` already in the config and
    qualifying completed and removed items, `init` and then `check`
    succeed. The generated tables show blank Summary cells, and
    `backlog.json` holds `null` for the four keys.
  - The same fixture through TRL0038's local sequence, with `legacy` set
    before `init --switch-to-local`: the tables and `backlog.json` under
    `.generated/` show the same blanks and nulls.
  - Output for a repo without `legacy` is unchanged (the existing pinned
    committed-output test stays green).
- `npm run backlog:check` and `node --test` exit 0.

## Notes

- Rejected: backfilling the archive. The milestones of about 900 old items
  were never recorded, and inventing them would put false history in the
  index.
- Rejected: dropping the requirement for every closed item. New closures
  would lose the historical snapshot SPEC §5.1 exists to keep.
- `closedBefore` is exclusive (2026-11-19 review). With an inclusive
  adoption date, an item open at cutover could close later that same day
  and skip its snapshot.
- `depends_on` stays required below the cutoff. The adopting repo adds `[]`
  where it is missing, which is a mechanical fix with no invented meaning.

- Release: no version bump here. TRL0040 carries 0.3.0 on the same
  branch and PR, so this change ships as part of that release.

## Risks

- Someone raising the cutoff to silence new errors. Mitigation: the SPEC
  text says the cutoff is set once, at adoption, to the highest id that
  existed then.

## Refinements

Decisions taken at plan time (2026-11-20). Each carried finding was checked
against the code. Threat model as in SPEC §3.1: cooperating writers and
trusted config. Unusual layouts are refused, not handled. Scan and committed
mode stay byte-for-byte unchanged for a repo without `legacy`.

Stale or tightened points in the story, checked against the code:

- `checkHistorical` and the close-date check live in `makeValidators` and
  `readBacklog` (`src/backlog.mjs`). `makeValidators` is shared with the
  ledger create preflight, which calls only `checkActive`, so a change
  confined to the closed-item path cannot reach it.
- The table builders already print `cell(undefined)` as an empty cell and
  `buildBacklogJson` already writes `?? null`. The only gaps are a blank
  string (`""` or `"   "`), which `??` keeps, and `effort: ""`. The fix is
  one place: the read step clears a blank field on a qualifying item. No
  renderer changes, so committed and local output agree by construction.
- `attachEffort` fails quietly on a blank effort, so no effort display
  fields are attached and `effortFields` already omits them. An archived
  `_effortLabel`, `_effortEmoji` or `_effortImage` key would survive the
  read as an extra front-matter key, so Step 2 explicitly clears all
  three on a qualifying item with missing or blank effort.
- `validateConfig` is the single rule set: `loadConfig`, init's kept
  config and TRL0038's switch (which validates the config it would write)
  all call it. Adding `legacy` there covers every caller. The switch keeps
  unknown config keys when it rewrites the config, so `legacy` survives it.
- `scripts/trellis-init.mjs` already refuses `--force` on a local config
  through `assertNotLocalMode`; the `legacy` refusal is a sibling of it,
  not new machinery.
- `idPrefix` is interpolated into a regex unescaped in scan mode, so
  `through` is checked by `startsWith(idPrefix)`, then a fixed `/^\d+$/`
  on the remainder with length `idWidth`, then a lexical compare of the
  fixed-width digit suffixes (same length, so lexical equals numeric).
  Never `Number`: scan mode sets no upper bound on `idWidth`, so widths of 16 or more
  pass past 2^53. No new
  regex is built from config text.
- Design cut: `legacy` requires a plain `idPrefix` (`PLAIN_PREFIX_RE`,
  already exported from `src/backlog.mjs` and used by ledger mode). The
  scan regex interpolates `idPrefix` unescaped, so `T.P` or `T+P` could
  skip or mis-match archive files. Refusing them with `legacy` is simpler
  than handling them, and repos without `legacy` are unchanged. SPEC §7
  and `docs/import.md` (Step 5) state it.
- `planScaffold` warns "use --force to overwrite" when supplied flags
  conflict with a kept config. With `legacy`, `--force` is refused, so
  Step 3 drops that hint there.
- `src/mcp.mjs` `moveTask` checks only the date shape, then re-reads the
  backlog. In a repo with `legacy` an impossible date is caught by that
  re-read and rolled back, so MCP needs no code change. Step 2 adds a
  test that pins it.

Carried findings, each confirmed against the code:

- **Blank value applies to every closed item in an opted-in repo.**
  Accepted. Without it, a non-qualifying `summary: "   "` would pass the
  strict path while a qualifying one renders blank, which is incoherent.
  Today `!it.summary` lets `"   "` pass, so this is a deliberate change,
  scoped to repos with `legacy` and listed in Scope as the second
  difference.
- **Attribute the milestone, priority and effort requirement to import
  planning, for every profile including `trellis`.** Accepted. The check
  is in the engine, so it holds for any profile. Scope and the import
  guide now say so.
- **Set `generatedArtifacts` to `committed` in the forced-init fixture.**
  Accepted. The fixture must not be in local mode: otherwise
  `assertNotLocalMode` fires first and the test would not exercise the
  `legacy` refusal.
- **Run the positive fixture through the local migration sequence.**
  Accepted as a test-only step. It reuses the switch-local fixture helper
  and the existing sequence; no code change is expected.

Rejected or narrowed from the story:

- **"With `--force`, init validates with the replacement and refuses a
  mismatch" needs no new code.** That is today's preflight. Only the
  unconditional refusal for an existing `legacy` config is added, and it
  does not depend on `tasksDir`. A custom-`tasksDir` fixture is still the
  test, plus one default-`tasksDir` case in the same `for...of` loop that registers a test per case (`node:test` has no `it.each`).
- **"An impossible close date on any item" means any completed or
  removed item.** Active items have no close date.
- **Unknown keys inside `legacy` are errors.** Added, to catch a
  misspelled `closedBefore` that would otherwise silently disable the
  exemption.
