# TRL0039 — Accept closed items that predate a repo's adoption

## Problem

`readBacklog` in `src/backlog.mjs` (`checkHistorical`) requires `summary`,
`milestone`, `priority` and `effort` on every completed and removed item.
`trellis init` refuses to scaffold a repo whose backlog has errors.

Taproot's backlog is already Trellis-shaped, but its archive is older than
those rules. On 2026-11-19, `trellis check` on a copy of it reported 1,995
errors:
- 873 completed items missing `milestone`;
- 768 missing `summary`;
- 103 missing `priority` and `effort`;
- 132 removed items missing `milestone`, and 13 missing `summary`.

The only way through today is to make up values for about a thousand
finished tasks.

## Scope

- **Config (SPEC §7).** A new optional object, `legacy`, has two
  required fields:
  - `through`, a full id in the repo's format (for example `TR01388`);
  - `closedBefore`, a real calendar date (`YYYY-MM-DD`, checked as a date,
    so `2026-02-31` is a config error): the adoption date, exclusive.

  Validation requires both, and `through` must match `idPrefix` and
  `idWidth`. The key is added under `specVersion` 2.5, which TRL0037 owns.
  This story merges after TRL0038.
- **Who qualifies (SPEC §5.1, §8.3).** A completed or removed item
  qualifies when both are true:
  - its id is at or below `legacy.through`;
  - its recorded `completed_on` or `removed_on` is a real calendar date
    strictly before `legacy.closedBefore`.

  An item that is still open at adoption and closes on adoption day or
  later fails the date test, so it must carry the full snapshot.
- **Close dates.** A repo without `legacy` keeps today's date check (the
  `YYYY-MM-DD` shape). A repo with `legacy` also rejects an impossible
  close date on any item as an item error, since qualifying depends on it.
- **What qualifying changes.** For a qualifying item, `summary`,
  `milestone`, `priority` and `effort` are optional. A blank value, meaning
  an empty or whitespace-only string (quoted or not), counts as missing. Everything else is still enforced: `id`, `title`,
  `status`, `depends_on`, the close date and `removed_reason`. Items that
  do not qualify, and every active item, are validated exactly as today.
- **Rendering (SPEC §6.2, §6.3, §8.1, §8.2).** The four fields are nullable
  for a qualifying item:
  - in `backlog.json`, a missing or blank value is `null`, effort included;
  - the effort display fields (`effortLabel`, `effortEmoji`,
    `effortImage`) are omitted when effort is missing;
  - the generated tables show an empty cell.

  SPEC states this exception where it promises a resolved effort number.
- **Init (in-place onboarding).** `trellis init` validates the archive
  with the config it will keep, so a repo writes `legacy` into its config
  first and runs init without `--force`. Init's `--help` and
  `docs/import.md` say so. With `--force`, which replaces the config, init
  validates with the replacement and refuses a mismatch before writing.
  `init --force` is refused before any write when the existing valid
  config has `legacy`, because the replacement config's default
  `tasksDir` could point preflight at an empty tree.
- **Import is unchanged.** The importer's planning (`src/import.mjs`)
  requires milestone, priority and effort for every profile, including
  the built-in `trellis` profile, and keeps doing so. The import guide
  says `legacy` covers in-place onboarding of a Trellis-shaped backlog
  only.
- **Docs.** SPEC.md §5.1, §6.2, §6.3, §7, §8.1 and §8.2.

## Acceptance

- `node --test` covers these, with a fixture under `test/fixtures/` holding
  closed items that omit the four fields:
  - A completed item whose id equals `legacy.through`, without the four
    fields, validates. With them blank, including a quoted `"   "`, it
    also validates and emits `null`.
  - The same item one id above `through` fails with today's messages.
  - An item at or below `through` closed on the adoption date itself fails
    with today's messages.
  - A removed item inside both bounds without `removed_reason` still fails.
  - An item inside both bounds without `depends_on` still fails.
  - A missing or malformed `through`, or an impossible `closedBefore`,
    is a config error. With `legacy` set, an impossible close date on an
    item is an item error. Without `legacy`, today's behavior is
    unchanged.
  - `init --force` with a `legacy` config and a custom `tasksDir` is
    refused before any write.
  - Positive init fixture: with `legacy` already in the config and
    qualifying completed and removed items, `init` and then `check`
    succeed. The generated tables show blank Summary cells, and
    `backlog.json` holds `null` for the four keys, with no effort display
    fields.
- `npm run backlog:check` and `node --test` exit 0.

## Notes

- Rejected: backfilling the archive. The milestones of about 900 old items
  were never recorded, and inventing them would put false history in the
  index.
- Rejected: dropping the requirement for every closed item. New closures
  would lose the historical snapshot SPEC §5.1 exists to keep.
- `closedBefore` is exclusive (2026-11-19 review). With an inclusive
  adoption date, an item open at cutover could close later that same day
  and skip its snapshot.
- `depends_on` stays required below the cutoff. The adopting repo adds `[]`
  where it is missing, which is a mechanical fix with no invented meaning.

## Risks

- Someone raising the cutoff to silence new errors. Mitigation: the SPEC
  text says the cutoff is set once, at adoption, to the highest id that
  existed then.
