# TRL0039 — Accept closed items that predate a repo's adoption

## Problem

`readBacklog` in `src/backlog.mjs` (`checkHistorical`) requires `summary`,
`milestone`, `priority` and `effort` on every completed and removed item.
`trellis init` refuses to scaffold a repo whose backlog has errors.

Taproot's backlog is already Trellis-shaped, but its archive is older than
those rules. On 2026-11-19, `trellis check` on a copy of it reported 1,995
errors:
- 873 completed items missing `milestone`;
- 768 missing `summary`;
- 103 missing `priority` and `effort`;
- 132 removed items missing `milestone`, and 13 missing `summary`.

The only way through today is to make up values for about a thousand
finished tasks.

## Scope

- **Config (SPEC §7).** A new optional object, `legacy`, has two
  required fields:
  - `through`, a full id in the repo's format (for example `TR01388`);
  - `closedOnOrBefore`, an ISO date: the adoption date.

  Validation requires both, `through` must match `idPrefix` and `idWidth`,
  and the key is added under `specVersion` 2.5, which TRL0037 owns. This
  story merges after TRL0038.
- **Validation (SPEC §5.1, §8.3).** For a completed or removed item whose id
  is at or below `legacy.through`, and whose `completed_on` or `removed_on`
  is on or before `legacy.closedOnOrBefore`, `summary`, `milestone`,
  `priority` and `effort` are optional. Everything else is still enforced:
  `id`, `title`, `status`, `depends_on`, the close date and
  `removed_reason`. An item open at adoption that closes later fails the
  date test, so it must carry the full snapshot.
  Items above the cutoff, and every active item, are validated exactly as
  today.
- **Rendering (SPEC §8.1, §8.2).** A missing value renders as an empty table
  cell and as `null` in `backlog.json`, as optional fields already do.
- **Init and import.** `trellis init` validates with the target's config
  when one exists. Its `--help` and `docs/import.md` explain setting
  `legacy` before init on a backlog with an older archive.
- **Docs.** SPEC.md §5.1 and §7 document the key.

## Acceptance

- `node --test` covers these, with a fixture under `test/fixtures/` holding
  closed items that omit the four fields:
  - A completed item inside both bounds, without the four fields,
    validates.
  - The same item one id above `through` fails with today's messages.
  - An item at or below `through` but closed after `closedOnOrBefore`
    fails with today's messages.
  - A removed item inside both bounds without `removed_reason` still fails.
  - An item inside both bounds without `depends_on` still fails.
  - A missing or malformed `through` or `closedOnOrBefore` is a config
    error.
- `npm run backlog:check` and `node --test` exit 0.

## Notes

- Rejected: backfilling the archive. The milestones of about 900 old items
  were never recorded, and inventing them would put false history in the
  index.
- Rejected: dropping the requirement for every closed item. New closures
  would lose the historical snapshot SPEC §5.1 exists to keep.
- `depends_on` stays required below the cutoff. The adopting repo adds `[]`
  where it is missing, which is a mechanical fix with no invented meaning.

## Risks

- Someone raising the cutoff to silence new errors. Mitigation: the SPEC
  text says the cutoff is set once, at adoption, to the highest id that
  existed then.
