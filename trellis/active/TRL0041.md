# TRL0041 — Viewer: worktree overlay and open ledger claims

## Problem

A repo worked by several parallel sessions (one git worktree each) has
stories being written, edited and closed on branches that the served
checkout cannot see until they merge. The owner wants one board that shows
that in-flight work, and the ids handed out by the ledger (TRL0037) that
have no file yet. TRL0005 builds the board over the served tree only.

## Scope

- **Lanes.** `git worktree list --porcelain` names every worktree. Every
  worktree other than the served one is a lane.
  - Bare, missing and prunable entries are listed under `unreadable` and
    skipped.
  - A lane on a detached HEAD gets the label `detached@<short sha>`. Each
    lane is identified by its worktree path, so two detached lanes never
    merge.
  - When the served directory is not a git repo, or git is missing, the
    board shows the served tree only and lists the reason under
    `unreadable`.
- **Comparison.** Each lane's task tree (its committed state plus its
  uncommitted working tree) is compared with the tree at `git merge-base
  <served HEAD> <lane HEAD>`, so items changed on the served branch after
  the lane branched are not lane edits.
  - Each side reads its own `trellis/backlog.config.json` for `tasksDir`,
    `idPrefix` and `idWidth`. When the merge-base has no Trellis config,
    when there is no merge-base (an orphan lane), or when either checkout
    has an unborn HEAD (no commit yet), the baseline is empty and every
    lane item counts as new. Any other git failure lists the lane under
    `unreadable`.
  - Relative to the merge-base, an item's change is `moved` when it sits
    in a different status folder, otherwise `edited` when its front matter
    or body changed, otherwise `new` when it is absent there. `moved` wins
    over `edited`, because a move also changes `status`.
  - A lane whose task tree fails validation is listed with its error count
    under `unreadable` and not merged in.
- **Resolution.** The board and `/api/backlog` show one task per id.
  - `tasks` and `counts` describe the resolved set: the served item, or,
    for an id that only lanes hold, the lane version.
  - When several lanes change one id, the card shows the served version
    when one exists. Otherwise it shows the version from the lane whose
    copy changed most recently: for a committed version, the committer time
    of the last commit that changed the file; for an uncommitted version,
    the file's mtime. Ties go to the ascending worktree path. Every
    changing lane adds a badge, whatever version is shown.
  - Each `inFlight` entry carries `{id, lane, branch, change, task}`,
    where `task` is that lane's full `backlog.json`-shaped record. TRL0008
    can then read a lane's `depends_on`, `status` and `effort`.
  - `/task/<ID>` shows the resolved version with every lane badge, and
    links to each lane's version (`/task/<ID>?lane=<slug>`, where the slug
    is derived from the worktree path, so it is stable across rebuilds).
- **Lane-only details.**
  - Task routes look the id up in the resolved item map, or in the
    selected lane's own parsed items for `?lane=`, so a lane id with a
    different prefix or width still resolves. Only an id in neither map
    is 404.
  - An active lane-only task whose milestone is not in the served config
    keeps the served milestone order, and its milestone is appended after
    the served ones (in first-seen order by worktree path) on the board,
    in the filter options and in the API `milestones` list. It does not
    land under "Needs attention".
  - Effort images come from the worktree that supplied the displayed
    version, under that worktree's `<tasksDir>/assets/` and with TRL0005's
    containment check.
  - In scan mode, `nextId` stays the served checkout's scan preview (SPEC
    §3), which may equal a lane-only id in `tasks`. The API says so in a
    `nextIdScope: "served"` field. Only `trellis claim` allocates across
    worktrees.
- **API additions.** This story adds `inFlight`, `claims` and `unreadable`
  to TRL0005's `/api/backlog`, and makes `tasks` and `counts` the resolved
  set.
- **Ledger claims.** In ledger mode (TRL0037), with a valid ledger, which
  means TRL0037's full check (the ref exists, is not symbolic, and its tip
  is a ledger), used for both claims and `nextId`:
  - `claim`-kind lines (not `seed` or `through`) with no item file in any
    worktree appear. "No item file" uses TRL0037's filename-only matching
    applied with each readable worktree's own `tasksDir`, `idPrefix` and
    `idWidth`, so a file in a lane that fails validation, or under a lane's
    different `tasksDir`, still closes the claim. These claims appear in a "Claimed, not written" list with id, date,
    branch and title;
  - `/api/backlog` adds `claims: [{id, date, branch, title}]`.

  A ref whose tip is not a ledger is listed under `unreadable`, and the
  board still renders.
- **Reload.** On top of TRL0005's watchers:
  - each lane's task directories and `trellis/` folder;
  - the directory holding each worktree's `HEAD`, and the parent
    directories of its checked-out branch ref, re-armed down nested paths
    as they appear. Git replaces loose refs and `HEAD` by rename, and a
    branch ref may start packed, so file-level watches would miss updates.
    A branch switch at the same commit therefore updates the badge;
  - `<git-common-dir>`, filtered by name for `packed-refs` and
    `worktrees`, so the first linked worktree is seen;
  - `<git-common-dir>/refs`, filtered by the ledger ref's first path
    component (`trellis` for `refs/trellis/ids`) and re-armed one level
    down at a time, so a ledger seeded after start-up is seen;
  - `<git-common-dir>/worktrees`, so lanes added or removed after start-up
    are picked up, with the lane list re-read and watchers re-armed.
- **Release.** This story merges after TRL0005 and bumps `package.json`
  and `package-lock.json` from 0.3.0 to 0.4.0 in its PR. That publishes
  the viewer release.

## Acceptance

- `node --test` covers these, using a temporary repo with linked
  worktrees:
  - New, edited and moved items in a lane come back with that lane's
    branch, before and after the lane commits them. A valid close reports
    `moved`.
  - An item edited on the served branch after the lane branched is not a
    lane edit.
  - After the served checkout merges a lane, that lane's merged edits lose
    their badges.
  - Two lanes changing one id give one card, the documented version (by
    commit time, not checkout mtime), and both badges.
  - `tasks` and `counts` include a lane-only item, and an `inFlight`
    entry carries its full record.
  - Both task links (`/task/<ID>` and `?lane=`) for a lane-only item with a
    different id width return 200.
  - A lane-only item with a milestone missing from the served config
    appears under that appended milestone.
  - A detached lane is labeled `detached@<sha>`. An orphan lane's items
    are all new, including before its first commit.
  - Deleting a lane's directory leaves the board rendering with that lane
    under `unreadable`. So does pointing the ledger ref at a non-ledger
    commit, or making it symbolic.
  - A claim whose file exists in a lane with invalid front matter, or under
    a lane's different `tasksDir`, is not listed as open.
  - With the page connected:
    - seeding a ledger and then claiming an id makes the claim appear
      without a manual reload;
    - adding the first linked worktree, from a branch that already holds a
      lane-only task, makes that task's card and badge appear without a
      manual reload.
  - Two successive ref-only updates (branch switches at the same commit,
    no task-file change) each update the badge.
  - In scan mode, `nextId` can equal a lane-only id, and `nextIdScope` is
    `"served"`.
- Run by hand in this repo with one linked worktree: start with an item
  present in both checkouts and unchanged, edit its title in the lane, and
  within two seconds the card shows its lane badge, the card keeps the
  served title, and the badge's link shows the edited title.
- `npm run backlog:check` and `node --test` exit 0.

## Notes

- Split from TRL0005 on 2026-11-19 after review: the overlay roughly
  doubled that story's surface, and the two parts can be reviewed and
  built apart.
- Read-only, like the rest of the viewer: nothing here writes a file or a
  ref.

## Risks

- Git calls per rebuild across many lanes. Mitigation: cache each lane's
  merge-base result keyed by both the served HEAD and the lane HEAD, so a
  served merge of the lane recomputes it. Re-run `git` only for lanes
  whose HEAD, served HEAD or files changed.
