# TRL0005 — Build the multi-backlog viewer (`trellis serve`)

## Problem

The owner keeps several Trellis backlogs: Taproot (`TR`, ledger ids, local
generated artifacts, spec 2.5), Espalier in `taproot-controls` (`ESP`, spec
2.3), good-agent (`GA`), arboretum (`ARB`), shywellness.com (`SHY`) and this
repo (`TRL`). The only way to read them today is each repo's generated
Markdown index. The owner wants one viewer that shows all of them at once,
stays current with each repo's main worktree, and is built from Espalier
controls with an `esp-repeater` of tasks. This story is view only: managing
tasks from the viewer is later work.

## Scope

- **Command.** `trellis serve [--config <file>] [--repo|--target <path>]
  [--port <n>] [--bind <address>] [--allow-host <name>]...` starts a
  `node:http` server, prints the URL and the config file it loaded (or
  "no config file; serving <repo>"), and runs until stopped. Wire it through `scripts/trellis.mjs` with a
  `--help` entry. The server code adds no runtime dependency.
  - `--repo <path>` serves that one repo, as a one-entry config. It cannot
    be combined with `--config`; passing both is a usage error (exit 2).
  - Without either flag, the config path is `$TRELLIS_VIEWER_CONFIG`, then
    `$XDG_CONFIG_HOME/trellis/viewer.json`, then
    `~/.config/trellis/viewer.json`. When none exists, `serve` serves the
    current directory's repo, as `--repo .`.
  - The default port is 4747, and `--port 0` picks a free one. The default
    bind address is `127.0.0.1`. When the effective bind (from `--bind` or
    the config) is not a loopback address, startup prints a warning that
    the backlogs are exposed beyond this machine.
  - The printed URL always passes the Host check: `http://127.0.0.1:<port>`
    for a loopback or wildcard bind (`0.0.0.0`, `::`), otherwise the bind
    address itself, which is then also an allowed host. Any other name a
    browser uses, such as a proxy's, needs `--allow-host` or
    `allowedHosts`.
- **Viewer config.** A JSON file whose root is an object:

  ```json
  {
    "backlogs": [
      { "id": "taproot", "name": "Taproot", "path": "~/Documents/GitHub/taproot" },
      { "id": "espalier", "name": "Espalier", "path": "~/Documents/GitHub/taproot-controls" }
    ],
    "port": 4747,
    "bind": "127.0.0.1",
    "allowedHosts": ["trellis.test"]
  }
  ```

  - `backlogs` is required and non-empty. Each `id` matches
    `^[a-z0-9][a-z0-9-]{0,39}$` and is unique; `name` is a non-empty display
    string; `path` is absolute or starts with `~/`. The array order is the
    display order.
  - `port`, `bind` and `allowedHosts` are optional. `--port` and `--bind`
    override the config value; each `--allow-host` adds a name to
    `allowedHosts`, so a dev environment can add its own host name without
    editing the owner's config.
  - An unknown top-level or entry key, a bad type, or a duplicate `id` is a
    startup error (exit 1) naming the key, so a typo is never silently
    ignored.
  - The config is read once at startup. Changing it needs a restart, which
    `--help` says.
  - `README.md` documents the file with this example, and
    `templates/viewer.example.json` ships it.
- **Main worktree.** Each entry's `path` resolves to its repo's main
  worktree, so the viewer always shows main even when the path names a
  linked worktree.
  - The server runs `git -C <path> worktree list --porcelain -z` (with
    `GIT_NO_LAZY_FETCH=1` and no network) and takes the first entry, which
    git always lists as the main worktree. This holds for a clone made with
    `--separate-git-dir` too, because git records the real checkout. A
    first entry marked `bare`, a path that does not exist, or a path
    outside any git repository is that backlog's error; the other backlogs
    still serve.
  - `worktree list --porcelain -z` needs git 2.36 or later. `--help` and
    `README.md` state that floor, and an older git makes the backlog's
    error name it. A ledger-mode backlog also needs TRL0037's floor (git
    2.45.1 and the `files` ref format) for its `nextId`; when that is not
    met, `nextId` is `null` with the ledger's reason.
  - The served tree is the main worktree's files on disk, including its
    uncommitted edits, never a branch ref. Cards, task views, search and
    watches read only the main worktree.
  - The one exception is a ledger-mode `nextId`. It is TRL0037's preview
    (`preview` in `src/ledger.mjs`), which scans every worktree of the
    clone so it never promises an id a lane already used. So a task that
    exists only in a linked worktree can move `nextId` while no card shows
    it.
- **Per-backlog reading.** Each backlog is read with its own repo's
  `trellis/backlog.config.json` and roster through `readBacklog`
  (`src/backlog.mjs`), so prefixes, milestones, effort scales and spec
  versions can differ between backlogs. The viewer never reads a committed
  `backlog.json`, so either `generatedArtifacts` mode (TRL0038) works.
  - Each backlog's record carries the `buildBacklogJson` shape. Its
    `nextId` follows TRL0037's rules: the scan value in scan mode; in
    ledger mode, the ledger preview computed through `src/ledger.mjs` when
    the ref is a valid ledger, otherwise `null`. The preview is computed on
    every request for that backlog, never cached, because a claim moves the
    ledger without touching any task file.
  - An unusable config for one backlog is any `loadConfig` error or failed
    config validation (including a JSON root that is not an object, such as
    `null`, and valid JSON without `milestones`). It makes only that
    backlog an error: its API record returns the config errors with status
    `error`, the interface shows them on that backlog, and every other
    backlog still serves. `validateConfig` gains a root guard that reports
    a non-object root as a config error; the guard also changes
    `init --force` and `init --switch-to-local` over a raw `null` config
    from a crash to a config error, and with `--force` to a rewrite.
  - Items whose front matter parsed render even when they fail validation.
    Files that did not parse (for example unterminated front matter) are
    listed in that backlog's diagnostics instead. Every record, route,
    search result and API entry uses the filename id, which the scan
    already checked against `idPrefix`/`idWidth`, never the authored `id`
    field. When one filename id appears in more than one status folder,
    the canonical copy is the most-closed copy that parsed (`removed/`,
    then `completed/tasks/`, then `active/`), and diagnostics list the
    other paths. A copy that is unreadable or did not parse never wins: it
    is only a diagnostic, so a valid active copy beside an unreadable
    completed one still shows as active, with the diagnostic. Active items that cannot be grouped (a missing or unknown
    milestone) get a "Needs attention" flag.
  - Completed and removed items render whatever their metadata. A null
    `summary`, `milestone`, `priority` or `effort` (TRL0039's legacy items)
    is a blank field with no effort display, search treats a null
    `summary` as empty, and such items never get "Needs attention".
- **API.** All JSON, all `GET`:
  - `GET /api/backlogs` lists every configured backlog in config order with
    `id`, `name`, `path`, the resolved `mainWorktree`, `status` (`ok` or
    `error`), `errors`, item counts by status and `nextId`.
  - `GET /api/backlogs/<id>` returns that backlog's full record: the
    `buildBacklogJson` shape, `nextId`, `config` (milestones in order, the
    effort scale, `idPrefix`) and `diagnostics`. An unknown backlog id is
    404.
  - Every task record in these responses carries `dependsOnMissing: true`
    when its front matter has no `depends_on` key, because the backlog
    shape serializes a missing list as `[]` (TRL0008 needs the
    difference).
  - `GET /api/backlogs/<id>/tasks/<ID>` returns one task's record with its
    front matter and `bodyHtml`, the body rendered by `src/markdown.mjs`.
    The task id is checked against that backlog's `idPrefix`/`idWidth` and
    looked up in its parsed item set, never used to build a file path. An
    unknown id is 404.
  - `GET /events` is a Server-Sent Events stream. Each message names the
    changed backlog (`{"backlog":"<id>"}`), and the page refetches only
    that backlog. The stream stays available while a backlog is in error.
  - `GET /assets/<backlog>/<path>` serves effort images only, from that
    backlog's `<tasksDir>/assets/`.
  - `GET /api/search?q=<term>&backlog=<id>[&backlog=<id>...]` searches the
    named backlogs (all when none is named) on the server, from the cached
    item reader, so the page never downloads every body. Ranking lives in
    one module, `src/search.mjs`, which the route uses.
    - The trimmed `q` matches as one case-insensitive substring. An empty
      `q` returns `[]`.
    - Each task yields at most one hit, for its best field: exact id, then
      partial id, then title, summary and body. Ties keep backlog config
      order, then id.
    - Each hit has `backlog`, `id`, the matched `field`, and `line` as text:
      the title for an id or title hit, otherwise the first matching line
      of that field.
    - An unknown `backlog` id is 404. A backlog in error is skipped and
      named in the response's `skipped` list, beside `hits`.
  - `GET /app/<file>` serves the built files in `viewer/dist/` with their
    content type and long-lived caching for hashed names. It serves only
    files the build wrote there (no directory listing, no path outside
    `viewer/dist/`), and the Host check and the 405 rule apply to it as to
    every route.
  - Every other path under `/api/` is 404, and a write method on any route
    is 405.
- **Interface.** A single-page app in `viewer/`, in plain JavaScript
  modules (`.mjs`, no TypeScript toolchain), written with Lit and
  `@taprootio/espalier`, wrapped in `<esp-root>` and following Espalier's
  documented component and token rules: no custom element of its own
  replaces an Espalier component that exists for the job, and styles use
  only Espalier's public tokens.
  - **Shell.** An Espalier page with a header naming the viewer and the
    backlog filter, and a light/dark scheme that follows the browser.
  - **Task list.** One `esp-repeater` (virtualized, `scroll-model="page"`)
    holds the task cards for every selected backlog at once. Each card
    shows the backlog name, id, title, summary, milestone, priority,
    effort, owner and status, using `esp-badge` for backlog, status,
    milestone and priority, and plain text in the card for the rest.
    Cards sort by backlog in config order, then milestone in that
    backlog's config order, then id. The repeater's `empty` slot says no
    task matches the filters.
  - **Filters.** `esp-pick-some` for backlog (all by default), status
    (active, completed, removed; active by default) and milestone, and
    `esp-pick-one` for priority and owner, plus an inline `esp-input
    input-type="search"` (not the `esp-search` overlay). Filter
    values are kept in the query string, so a filtered view is a link.
    Milestone values are grouped by backlog, because two backlogs can name
    milestones differently. Owner values are trimmed and case-folded with
    the roster's rules before matching and deduplication.
  - **Search.** The search field calls `GET /api/search` for the selected
    backlogs: case-insensitive term matching over id, title, summary and
    body. An exact id match ranks first, then a partial id match, then
    title, summary and body hits, in that order. While a search term is
    set, the repeater shows the hits in that order instead of the default
    sort, still narrowed by the other filters, and each card adds its
    matching line.
  - **Task view.** `/b/<backlog>/task/<ID>` shows one task: front matter
    as a header and `bodyHtml` as the body. The page inserts only
    `bodyHtml` as HTML; every other value is set as text. A back control
    returns to the list with its filters.
  - **Effort.** Effort follows SPEC §6.3, which TRL0015 deferred to the
    viewer: under a custom scale, every task whose effort resolves shows
    `label · N`, plus the configured emoji or the configured image from
    `/assets/<backlog>/…`, with the label as the image's alt text. An
    effort that does not resolve shows an empty field. It shows a
    validation error only when the shared validator rejects it, so a
    completed task with a retired effort label (valid under SPEC §8.3) has
    no error.
  - **Errors and diagnostics.** A backlog in error shows its errors in an
    `esp-info intent="danger"` above the list, and its other backlogs' cards still
    show. A backlog's diagnostics show in an `esp-details` whose `summary`
    states their count and whose content lists them, and an `esp-badge`
    beside it shows the "Needs attention" count.
  - **Live.** The page opens `/events` and refetches the named backlog,
    keeping the scroll position and filters; while a search term is set,
    it also re-runs the search, and an open task view refetches its
    `/api/backlogs/<id>/tasks/<ID>` record, because the backlog record has
    no `bodyHtml`. When the stream drops, it reconnects and refetches every
    backlog, the open search and the open task. Search requests are debounced (250 ms) while
    typing, and a response older than the latest request is discarded.
  - Every route the app owns (`/`, `/b/<backlog>`,
    `/b/<backlog>/task/<ID>`) returns the app's HTML shell; the server
    never renders task data into HTML other than `bodyHtml`. `/b/<backlog>`
    is the list with the backlog filter preset to that backlog, as it would
    be through the query string.
- **Build and packaging.** `npm run build:viewer` bundles `viewer/` with
  Lit and Espalier into `viewer/dist/` with one bundler, a pinned
  devDependency (rolldown, which Taproot and Espalier already use). Lit,
  `@taprootio/espalier` and the bundler are exact-pinned devDependencies,
  so the published package still has no new runtime dependency.
  - `prepack` runs the build, and `viewer/dist/` is git-ignored. The
    implementation change does not add `viewer/dist/` to `package.json`
    `files`, so no release can carry the Espalier bundle before the grant;
    the grant change adds it (see Release).
  - `trellis serve` from a checkout without `viewer/dist/` exits 1 with a
    message naming `npm run build:viewer`. The server module takes the
    dist directory as a parameter (default `viewer/dist/`), so a test can
    point it at an empty one.
  - The package test runs `npm run build:viewer` itself before packing, so
    `node --test` passes on a fresh checkout as well as in `release.yml`.
  - The build copies the installed Espalier package's `LICENSE` to
    `viewer/dist/ESPALIER-LICENSE.md` and its `licenses/` folder
    (`THIRD_PARTY_NOTICES.md`, `GOOGLE_FONTS_NOTICES.md`,
    `ASSET_PROVENANCE.md` and the rest) to `viewer/dist/licenses/`, so the
    bundle always carries the notices of the exact pinned version.
  - `release.yml` runs `npm run build:viewer` between `npm ci` and
    `node --test`. The package test asserts that `viewer/dist/` is packed
    exactly when `package.json` `files` lists it, and that whenever it is,
    `viewer/dist/ESPALIER-LICENSE.md`,
    `viewer/dist/licenses/THIRD_PARTY_NOTICES.md` and the grant file
    `viewer/ESPALIER-GRANT.md` are packed too, so a bundle can never
    publish without its grant.
- **Licensing (owner decision 2026-11-21).** The package bundles Espalier,
  which is proprietary, inside MIT-licensed Trellis.
  - The grant that lets Trellis users run the bundled Espalier is the
    owner's to write and approve, as `viewer/ESPALIER-GRANT.md`. An
    implementation draft is not that approval.
  - The grant change, not the implementation change, adds the grant file,
    the `files` entry, and the `README.md` and `package.json` text saying
    the bundled viewer is covered by that grant and Espalier's license
    while Trellis's own code stays MIT.
- **Escaping.** Every repository-derived value that reaches HTML (titles,
  front matter, summaries, search excerpts, owner handles, backlog names)
  is set as text. `bodyHtml` is the only HTML, and `src/markdown.mjs`
  escapes everything in it.
- **Markdown rendering.** A small in-repo renderer (`src/markdown.mjs`)
  covers headings, paragraphs, lists, code spans and blocks, links,
  emphasis and tables, escaping all HTML. Markdown it does not cover is
  shown as text.
  - Repository-relative targets are first resolved against the source
    item's directory on disk (for example `<tasksDir>/active/`), then
    looked up in that backlog's scanned task set. Other targets are parsed
    with `new URL(target, <viewer origin>)`. Only `http`, `https` and
    `mailto` targets, and relative targets that resolve to the viewer's
    own origin, are kept. Anything else, including a target that
    normalizes to another host (`//host`, `/\host`), renders as plain
    text.
  - A relative link to a known task file of the same backlog (for example
    `../active/TRL0012.md`) is rewritten to `/b/<backlog>/task/<ID>`.
    Other repository paths render as plain text.
- **Host check.** A request whose `Host` header is not
  `127.0.0.1:<port>`, `localhost:<port>`, or exactly one of `allowedHosts`
  (a bare host name, matched case-insensitively, with or without any
  port) gets 403, so a DNS-rebinding page cannot read the backlogs. The
  check runs before every other check.
- **Read-only.** No route changes a file, a ref or git state, and the
  server never fetches.
- **Live reload.** Per backlog, non-recursive `fs.watch` watchers on its
  main worktree send an SSE message naming the backlog, debounced to
  250 ms. Recursive watching is not used, because Linux lacks it on the
  package's Node 18 floor.
  - They watch the tasks root, `active/`, `completed/`,
    `completed/tasks/` and `removed/`, plus `trellis/` for the config and
    roster. When the tasks root itself is missing, they watch its nearest
    existing ancestor, and they re-attach when a directory is replaced at
    the same path.
  - A directory that does not exist yet is armed when its parent reports
    it. After every rebuild, any missing or errored watcher is re-armed,
    so a branch switch in the main worktree that removes
    `completed/tasks/`, or a first close that creates it, keeps reload
    working.
  - In ledger mode they also watch the directories that hold the ledger
    ref's loose file and `packed-refs` in the common git directory (the
    nearest existing ancestor when the ref's directory does not exist
    yet), because git replaces those files rather than editing them. So
    creating the ref and each later claim refresh `nextId`.
  - Generated files and `.generated/` are ignored.
- **Cache.** `readBacklog` gains an opt-in item reader (a parameter
  defaulting to today's file read). The viewer passes a cached reader,
  one per backlog, that returns front matter and body per file, keyed by
  path, size and mtime. Shared validation still runs over the result
  against that backlog's current config and roster.
  - The reader resolves each task path (`realpath`) before reading. It
    skips, with a diagnostics entry, any candidate whose resolved path
    leaves that backlog's main worktree or whose target is not a regular
    file (a FIFO, socket or device), so a task route cannot expose a file
    from elsewhere and a read can never block. On POSIX the reader opens
    each file nonblocking and checks the opened descriptor is a regular
    file before reading, so a file swapped for a FIFO after the path check
    cannot block. A task that disappears between listing and reading is a
    skipped candidate for that rebuild, not an error. The same guard covers
    every file the viewer reads: the config and roster (an unreadable one
    is a diagnostics entry, or that backlog's config error) and effort
    images (404).
  - Asset paths are checked after resolving symlinks, so a link pointing
    outside the asset root is 404. Image responses carry an explicit
    content type, and SVG responses also carry `Content-Security-Policy:
    default-src 'none'; style-src 'unsafe-inline'; sandbox`, so opening an
    SVG directly cannot run script on the viewer's origin.
  - Filename matching uses one shared matcher that treats `idPrefix`
    literally (escaped, not interpolated into a regex). Viewer routes and
    TRL0037's ledger scans reuse it.
  - Every path a watch event names is re-read regardless of mtime. An
    event without a filename, or one naming a directory that was removed or
    replaced, invalidates every cached item under that directory, so a
    replacement with the same paths, sizes and mtimes is re-read.
  - Each backlog's resolved asset root must itself stay inside its main
    worktree before any image path under it is checked.
- **Release.** `.github/workflows/release.yml` publishes on any push to
  `main` whose `package.json` version is not yet on npm, so the
  implementation change keeps the version at 0.3.0 and the story active.
  Once the owner has approved the grant text, the grant change adds the
  grant and the packaging above, bumps `package.json` to 0.4.0, and moves
  this story to `completed/tasks/` in the same change (SPEC §4). After it
  merges, check that `npm view @taprootio/trellis@0.4.0` shows the
  release with the viewer files; a failed publish is fixed on `main` like
  any release.
- **Out of scope.** Editing, claiming or moving tasks from the viewer;
  reading worktrees other than main (the removed TRL0041); deployment and
  SSO (TRL0012, TRL0013); the dependency graph and effort filter
  (TRL0008).

## Acceptance

- `node --test` covers these, using temporary repos:
  - With a config naming two repos, `GET /api/backlogs` lists both in
    config order with their counts, and each `/api/backlogs/<id>` returns
    its own prefix and milestones.
  - A config entry whose path is a linked worktree resolves to the main
    worktree: an item added only in the linked worktree is absent, and one
    added in the main worktree appears.
  - One entry with a missing path, one with a `null` config and one with a
    config without `milestones` each make only that backlog `error`, while
    the other backlog still returns its items.
  - An unknown config key, a duplicate `id`, a bad `id` and `--repo` with
    `--config` each fail at startup with the documented exit code.
  - With no flags and no config file, `serve` serves the current
    directory's repo; with `TRELLIS_VIEWER_CONFIG` set, it reads that file.
  - `--port 0` binds a free port, the default is 4747, and the listener is
    `127.0.0.1` unless `--bind` is given, which prints the warning.
  - `nextId` is the scan value in scan mode, `null` in ledger mode without
    a ref, and changes after a `trellis claim` with no task file touched.
  - A request with `Host: evil.example` gets 403; with `allowedHosts:
    ["trellis.test"]`, or with `--allow-host trellis.test` and no config
    key, `Host: trellis.test` and `Host: trellis.test:443`
    are served. A write method gets 405.
  - `GET /api/backlogs/<id>/tasks/../SPEC.md` and
    `GET /assets/<id>/../../package.json` are 404, with `tasksDir` set to
    a nested folder such as `docs/tasks`.
  - A `<script>` in a task body renders inert in `bodyHtml`.
    `[x](javascript:alert(1))`, `[x](//evil.example)` and
    `[x](/\evil.example)` render no link, and a link from one task to
    another task file of the same backlog goes to
    `/b/<id>/task/<ID>`, including under a nested `tasksDir`.
  - `init --force` over a raw `null` config rewrites it, and `init
    --switch-to-local` over one reports a config error, instead of
    crashing.
  - A legacy completed item with null summary, milestone, priority and
    effort is returned as completed, with no "Needs attention" flag.
  - An id in both `active/` and `completed/tasks/` returns the completed
    copy, and diagnostics list the active path. A file with unterminated
    front matter is a diagnostic, and an item whose authored `id`
    mismatches its filename is returned under its filename id.
  - A task file that is a symlink to Markdown outside the main worktree,
    or a FIFO, is skipped and listed in diagnostics, and the server stays
    responsive. A FIFO in place of the config or roster gives a
    diagnostic, and one in place of an effort image gives 404. An asset
    symlink pointing outside the root is 404, and an SVG response carries
    the sandbox policy.
  - With an `idPrefix` containing a regex metacharacter (such as `R+`),
    valid tasks appear and unrelated Markdown does not.
  - Removing and recreating `completed/tasks/`, and removing and restoring
    a nested `docs/tasks` and then editing a title, each send an SSE
    message naming that backlog and no other. A timestamp-preserving
    replacement of an item refreshes its title.
  - `GET /api/search` puts an exact id first and a title hit above a body
    hit, returns a body hit's matching line and an id hit's title, gives a
    task matching in title and body one title hit, searches only the named
    backlogs, returns `[]` hits for an empty `q`, 404 for an unknown
    backlog, and lists a backlog in error under `skipped`.
  - `GET /app/<file>` serves a built file with its content type, and
    `GET /app/../package.json` is 404.
  - The viewer's pure modules under `viewer/` (filter, sort, query-string
    state, effort display), the same files the bundle imports, are tested
    directly: sort follows backlog, then milestone order, then id; owner
    filters match with the roster's trim and case-fold rules; a custom
    scale gives `label · N`.
  - A ledger-mode backlog whose only higher id is a task in a linked
    worktree shows no card for it, while `nextId` is past it.
  - A `--separate-git-dir` clone resolves to its checkout, and a backlog
    whose first worktree is bare is an error.
  - With `--bind 0.0.0.0`, the printed URL is `http://127.0.0.1:<port>`,
    a request to it is served, and the warning prints; a config `bind` of
    `0.0.0.0` warns the same way.
  - A valid active copy beside an unreadable completed copy of the same id
    is returned as active, with a diagnostic.
  - A completed task with a retired effort label has no validation error.
  - Creating the ledger ref, then two claims in a row with no task edits,
    each send an SSE message naming that backlog.
  - A task removed between listing and reading is skipped without failing
    the rebuild, and a task file swapped for a FIFO after the path check
    does not block the server.
  - Replacing a watched directory with one holding files of the same
    paths, sizes and mtimes but different titles refreshes those titles.
  - The package test passes with `viewer/dist/` absent from `files`, and,
    in a temporary copy with it added, fails until the grant file is
    present.

## Notes

- **Revised 2026-11-21 at the owner's request.** The viewer serves several
  backlogs at once, reads only each repo's main worktree, uses Espalier

- **Interface tests.** Trellis has no browser test harness, and adding one

- Deployment and SSO stay deferred (TRL0012, TRL0013).

## Risks

- **Watch storms** during a branch switch in a main worktree. Mitigation:
  the 250 ms debounce and one rebuild per backlog per event batch.
- **Large backlogs** (Taproot has about 1,300 items, and all backlogs
  together more). Mitigation: the per-file cache, one rebuild per changed
  backlog, and the virtualized repeater.
- **Watcher limits.** Several repos multiply watched directories.
  Mitigation: only the listed directories per backlog, never recursive.
- **Espalier drift.** A later Espalier release can rename a component or
  token. Mitigation: the exact pin and a bundled build, so the viewer only
  changes when the pin moves.
- **Older specs.** Espalier's backlog is on spec 2.3. Mitigation: each
  backlog is read with its own config through the existing reader, and
  the two-repo test uses differing specs.
